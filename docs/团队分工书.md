# SplitWay · 团队分工书

> 版本：v1.0 — 2026-09-28
> 适用范围：V1（可复现环境 + 找搭子/建房间/记账/结算完整链路 + 安全基线）

---

## 一、角色总览

| 角色 | 代号 | 类型 | 一句话职责 |
|---|---|---|---|
| Project Owner | 肖宇翔 | 人 | 范围冻结、契约裁定、验收签字 |
| 主理人 / 架构共同负责人 | Gaster | AI | 编排、架构起草与冻结、跨角色信息中转 |
| 产品经理 | 天子 | AI | PRD、需求拆解、验收标准定义 |
| 后端工程师 | 神绮 | AI | 业务链路、安全基线、容器化 |
| 前端工程师 | 万兰 | AI | 页面实现、接口联调、前端容器化 |
| QA 工程师 | 神化 | AI | 测试用例、独立验收、越权断言 |
| 红队审计员 | 巅峰 | AI | 独立挑错，只报不改 |

**架构决策层 = Owner + Gaster。** 架构师岗不单独设人：Gaster 负责起草候选方案与权衡，**最终裁定与签字在 Owner**。这样任何一条架构结论都能追溯到"谁签的字"。

## 二、职责边界

### Owner（肖宇翔）

负责：范围冻结、契约裁定、决策签字、Issue 派发、Issue 关闭与 PR 合并。
不负责：任何专业产出（PRD / 代码 / 测试）。

### Gaster（主理人 / 架构共同负责人）

负责：任务编排与信息中转、架构与接口契约的起草与冻结、文档一致性把关、跨角色上下文传递。
不负责：代替工程师写代码、代替 QA 出验收结论。

### 天子（产品经理）

负责：`docs/PRD.md` 的产出与维护、需求优先级、**每条需求的验收标准（必须可执行）**、不做清单。
不负责：技术方案、代码。

### 神绮（后端工程师）

负责：`backend/` 全部实现、数据模型与迁移、接口契约的实现侧、后端容器化。
不负责：前端代码、前端容器化、`frontend/Dockerfile`。

### 万兰（前端工程师）

负责：`frontend/` 全部实现、页面与交互、接口联调、前端容器化（`Dockerfile` / `nginx.conf`）。
不负责：`docker-compose.yml`（由神绮独占，避免互相覆盖）。

### 神化（QA 工程师）

负责：测试用例编写与执行、**独立复跑 A/B/C 全部验收编号**、越权断言脚本、验收报告。
不负责：修改业务代码。发现问题只提交给对应工程师。

### 巅峰（红队审计员）

负责：独立挑错 —— 找漏洞、找逻辑矛盾、找"声明了但没做到"的地方。
产出：复审意见，逐条标 **成立 / 需修正 / 无法验证**。
**硬约束：只报不改。** 审计员与实现者必须是不同角色、不同会话，避免"自己给自己批卷子"。

## 三、协作流程

```
Issue（Owner 派发 + 打「状态:已批准」）
  → 设计进 docs
  → 契约冻结（architecture.md §5）
  → 实现（feature/<模块>-<简述> 分支 + PR）
  → 复审（巅峰 / 神化，按 BLOCK-n / SUG-n 编号）
  → 整改（按同一编号逐条回填）
  → 验收（神化独立复跑）
  → Owner 合并 main，Owner 关闭 Issue
```

### 开工门禁

| 规则 | 说明 |
|---|---|
| Issue 带 `状态:已批准` 才可开工 | `状态:待批准` 的不得开工 |
| `状态:待整改` 可直接改 | 无需重新申请 |
| 同一 PR 不得追加未讨论的新功能 | 新功能先开 Issue |
| 不得自行合并 PR | 合并权在 Owner |
| 不得自行关闭 Issue | 关闭权在 Owner |

## 四、硬约束（V1 全程有效）

1. **身份只来自服务端 Token 解析** —— 任何接口不接受 `userId` / `role` 等身份入参。路径中的 `member_id` / `post_id` 是资源标识，不属于身份入参。
2. **金额全程整数分** —— 不得出现 float 参与金额运算。换算只允许发生在前端输入框那一次。
3. **零硬编码凭据** —— `.env` 必须被忽略；仓库只允许 `.env.example` 且只有占位符；JWT 密钥缺失即启动失败，不提供默认值。
4. **CORS 永不使用 `"*"`** —— 白名单走环境变量。
5. **验证结果一律写「命令 → 结果」** —— 不写"应该没问题"。
6. **交付状态严格分级** —— 「已跑通 / 已实现未验证 / 未做」三档必须如实标注，不得把"未验证"写成"通过"。
7. **范围冻结** —— V1 三项定完即冻结，加功能走新 Issue。

## 五、回报格式

每位角色交付时按此结构回报，不带客套、不带修饰：

1. 文件清单（路径 + 一句话作用）
2. 执行过的命令 → 真实输出摘要
3. 验收对照表（逐条标三档状态 + 证据命令）
4. 契约疑问或偏离
5. 遗留问题

格式细则（PR 正文 / 复审意见 / 整改反馈）见 `docs/development-handbook.md` 附录 B。
