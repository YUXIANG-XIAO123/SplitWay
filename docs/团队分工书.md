## 三、协作流程

```
Issue（Owner 派发 + 打「状态:已批准」）
  → 设计进 docs
  → 契约冻结（architecture.md §5）
  → 实现（feature/<模块>-<简述> 分支 + PR）
  → 复审（按 BLOCK-n / SUG-n 编号）
  → 整改（按同一编号逐条回填）
  → 独立验收（复跑 A / B / C 编号）
  → Owner 合并 main，Owner 关闭 Issue
```

### 开工门禁

| 规则 | 说明 |
|---|---|
| Issue 带 `状态:已批准` 才可开工 | `状态:待批准` 的不得开工 |
| `状态:待整改` 可直接改 | 无需重新申请 |
| 同一 PR 不得追加未讨论的新功能 | 新功能先开 Issue |
| **不得自行合并 PR** | 合并权在 Owner |
| **不得自行关闭 Issue** | 关闭权在 Owner，且统一关闭，不逐个关 |
| PR 用 `Refs #n`，**不要用 `Closes #n`** | `Closes` 会在合并时自动关 Issue，绕过验收 |

## 四、硬约束（V1 全程有效）

1. **身份只来自服务端 Token 解析** —— 任何接口不接受 `userId` / `role` 等身份入参。路径中的 `member_id` / `post_id` 是资源标识，不属于身份入参。
2. **金额全程整数分** —— 不得出现 float 参与金额运算。换算只允许发生在前端输入框那一次。
3. **零硬编码凭据** —— `.env` 必须被忽略；仓库只允许 `.env.example` 且只有占位符；JWT 密钥缺失即启动失败，不提供默认值。
4. **CORS 永不使用 `"*"`** —— 白名单走环境变量。
5. **验证结果一律写「命令 → 结果」** —— 不写"应该没问题"。
6. **交付状态严格分级** —— 「已跑通 / 已实现未验证 / 未做」三档必须如实标注，不得把"未验证"写成"通过"。
7. **范围冻结** —— V1 三项定完即冻结，加功能走新 Issue。

## 五、回报格式

每人交付时按此结构回报，不带客套、不带修饰：

1. 文件清单（路径 + 一句话作用）
2. 执行过的命令 → 真实输出摘要
3. 验收对照表（逐条标三档状态 + 证据命令）
4. 契约疑问或偏离
5. 遗留问题

格式细则（PR 正文 / 复审意见 / 整改反馈）见 `docs/development-handbook.md` 附录 B。
