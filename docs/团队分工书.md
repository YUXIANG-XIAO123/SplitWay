# SplitWay · 分途 — 团队分工书

> 版本：V3.0
> 日期：2026-09-29
> 变更：参考 VeriLens 分工书的颗粒度重构 —— 补齐角色颗粒度（对接 / 模块任务 / 日常节奏 / 职责权重 / 技能要求 / 不负责）+ 协作规范（Kickoff 清单 / 文件边界 / 分支策略 / PR 规范 / 复审分工 / 状态机 / 评审分级 / 沟通渠道）
> 历史：V2.0（2026-09-29）团队重构为 3 名真人成员；V1.0（2026-09-28）首版

**核心理念**：SplitWay 不是"又一个记账 App"，而是一条**可被自动化验证的多人协作账目链路** —— 出行前把人凑齐（找搭子 → 建房间 → 审批），出行中把钱算清（记账 → 结算）；全程身份只信服务端、金额不碰浮点、每一步都有可执行的验收编号。

## 二、组织架构

```
                    肖宇翔
            Project Lead & Architect (Owner)
                        │
        ┌───────────────┴───────────────┐
        │                               │
     陈展鸿                           包伟榕
  Backend Engineer                Frontend Engineer
  （数据 / 接口 / 算法）             （页面 / 交互 / 联调）
        │                               │
        └───────────────┬───────────────┘
                        │
             独立验收 · 红队审计（待定）
```

**协作流向**：Owner 制定契约与口径 → 陈展鸿（后端）与包伟榕（前端）**并行推进**（前端按已冻结契约开发，不必等后端就绪）→ 各自提 PR → **交叉复审**（谁没写谁审）→ Owner 终审合并 → 阶段收口时由独立验收方复跑 A / B / C 编号。

**不设 `dev` 分支**：本项目按阶段推进，**阶段收口标志本身就是集成门槛**，再加一层 `dev` 只会多一次合并。分支策略见 §4.3。

## 三、各角色详细职责

### 3.1 肖宇翔 —— Project Lead & Architect（Owner）

**对接**：向上对齐项目目标（个人作品，能力证明为主，不做科研化功能）→ 向下制定契约与口径 → 对外承接项目叙事与技术问答。

**你的工作不是写业务代码，而是制定标准、维护契约、守住边界。**

#### 三大设计（核心职责）

| 设计 | 你做什么 | 别人做什么 |
|---|---|---|
| **接口契约**（`architecture.md` §5） | 定义全部路径 / 入参 / 出参 / 状态码 / 权限；**冻结后改动须由你裁定** | 陈展鸿按契约实现后端；包伟榕按契约对接前端；异议走 Issue 评论 |
| **数据模型与业务规则**（`architecture.md` §3–§4） | 表结构与约束、**金额全程整数分**、成员四态状态机、均分 + 最大余额法 | 陈展鸿实现迁移与算法；包伟榕按状态渲染 |
| **工程规范** | 分支 / Commit / PR 规范、`docs/` 文档规范、Issue 派发与放行、验收口径 | 全员遵循 |

#### 你负责制定、别人执行的

| 标准 / 规范 | 你制定 | 谁执行 |
|---|---|---|
| 接口契约 v1 | 路径、schema、状态码语义、权限归属（已冻结于 `docs/architecture.md` §5） | 陈展鸿 `#1`–`#6`、包伟榕 `#7`–`#10` |
| 金额与身份两条红线 | 整数分、元→分唯一换算点；身份只从服务端 Token 解析 | 全员，验收于 C1–C6 |
| 分摊算法口径 | 均分 + 最大余额法；余数按 userId 升序分配 | 陈展鸿 `#5` |
| PR / Issue / 标签规范 | 分支命名、PR 正文结构、`状态:` 标签流转（`handbook` 附录 B） | 全员遵循 |
| 验收口径 | A / B / C 编号与判定标准（`docs/PRD.md`） | 独立验收方按此复跑 |

#### 日常工作

| 时段 | 工作 |
|---|---|
| 收到 PR | 交叉复审后进行**终审**；重点看契约一致性与两条红线；结论写在 PR 评论 |
| 收到契约疑问 | 裁定并**先改 `docs/architecture.md`**，再让实现跟进 |
| 阶段收口 | 判定收口标志是否达成；达成后重新打开下一阶段 Issue 并放行 |
| 持续 | 防止范围膨胀：V1 三项已冻结，加功能走新 Issue |

#### 职责权重

- **架构与契约（40%）**：契约维护、数据模型、业务规则、工程规范
- **评审与集成（35%）**：PR 终审、合并把关、阶段收口判定
- **项目推进（25%）**：Issue 派发与放行、`docs/` 维护、范围控制

#### 技能要求

架构设计、契约与接口抽象、代码评审能力；Python / Vue 能读懂并写模板级示例即可（**不需要精通框架细节**）。

#### 不负责

- 不写后端业务实现 —— 陈展鸿做
- 不写前端页面 —— 包伟榕做
- 不代替验收方下验收结论 —— 验收以命令输出为准
- 例外：可写模板级示例；可改文档与规范（不改变他人产出的语义）

### 3.2 陈展鸿 —— Backend Engineer

**对接**：接收 Owner 的接口契约与数据模型 → 实现后端与迁移 → 向包伟榕提供稳定、契约一致的 API。

| 模块 | 具体任务 | Issue |
|---|---|---|
| **骨架与配置** | 仓库骨架、`.gitignore`（必含 `.env`）、`.env.example`、`docker-compose.yml`（db/backend/frontend 三服务）、Dockerfile、`config.py`（**缺关键环境变量即启动失败**）、Alembic 初始化 | `#1` |
| **认证** | register / login / me；`bcrypt` 哈希（**不用 passlib**）；JWT 签发与校验（密钥仅来自环境变量）；`get_current_user` 依赖 | `#2` |
| **搭子帖** | 发布 / 分页列表 / 详情（**含 `room_id`**）/ 删除（仅帖主） | `#3` |
| **房间与成员** | 建房间（仅帖主）、申请、审批 / 拒绝、退出；四态状态机；**部分唯一索引**迁移；`require_room_member` / `require_room_host` | `#4` |
| **账单与结算** | 均分 + 最大余额法（`services/split.py`）；账单增删；结算幂等；结算后只读 | `#5` |
| **测试** | pytest 覆盖全部接口；**`test_idor.py`（越权断言 403）与 `test_split_precision.py`（精度断言）为必做** | `#6` |

**技能要求**：Python、FastAPI、SQLAlchemy 2.0、Alembic、PostgreSQL 基础、Docker Compose 能跑通即可（不会的查 `handbook` + 在 Issue 里问）

**上手提示**：这条线验收特别清晰 —— `docker compose up -d db backend` 能起 → `pytest` 全绿 → 两个账号能真实走完整条链。依赖是一条直线，不用猜。

#### 日常节奏

| 时段 | 工作 |
|---|---|
| 开工 | 把 Issue 标签自己改成 `状态:实施中`（不用申请，见 §4.6）；建 `feature/<模块>-<简述>` 分支 |
| 开发 | 按契约实现；保持本地测试绿；**新增接口必须有对应用例** |
| 提 PR | 转 `Ready` 时把标签改成 `状态:待验收`；正文按 `handbook` 附录 B.1 写，附「命令 → 结果」 |
| 收到复审 | 按 `BLOCK-n` 编号逐条整改，用附录 B.3 格式回填；**不要自行合并** |

#### 职责权重

- **后端实现（60%）**：数据模型与迁移、认证、搭子帖、房间与成员、账单与结算
- **测试与自证（25%）**：pytest 用例、越权断言、精度断言、证据回填
- **联调与容器化（15%）**：接口联调、`docker-compose.yml` 维护、可复现环境

#### 不负责

- 不写前端页面与 `frontend/` 下任何文件（含 `Dockerfile`、`nginx.conf`）
- 不修改 `docs/architecture.md` §5 契约 —— 发现问题在 Issue 提出，由 Owner 裁定
- 不修改金额算法口径（只实现它）
- 不自行合并 PR、不自行关闭 Issue

### 3.3 包伟榕 —— Frontend Engineer

**对接**：接收 Owner 的接口契约 → 实现页面与交互 → 调陈展鸿的后端 API；发现问题回到 Issue，而不是改契约。

| 模块 | 具体任务 | Issue |
|---|---|---|
| **骨架与身份态** | Vite + Vue 3 + TypeScript + **Tailwind（唯一样式层）**；axios 实例与拦截器（自动带 Bearer、401 清 token 跳登录）；`useAuth`（**不引 Pinia**）；路由与登录守卫；注册 / 登录页 | `#7` |
| **列表与详情** | 找搭子列表（目的地 / 出发日期 / 需求人数 / 发起人 / 状态）+ 发帖；帖子详情：申请加入、帖主创建房间、申请人审批 | `#8` |
| **房间页** | 三分区：成员区（状态 + 房主审批 / 退出）、记账区（账单列表 + 新增，金额限两位小数）、结算区（触发结算、只读、幂等展示） | `#9` |
| **容器化** | 多阶段构建（node 构建 → nginx 托管）+ `nginx.conf`（静态托管 + `/api` 同源反代到 `backend:8000`，监听 80） | `#10` |

**技能要求**：Vue 3（Composition API）、TypeScript、Tailwind、axios 基础；不需要框架之外的重型状态管理经验

**上手提示**：接口契约已冻结在 `architecture.md` §5，**按契约开发即可，不必等后端跑起来**。金额字段一律是 `*_cents` 整数分，元→分只在你输入框那一处换算。

#### 日常节奏

| 时段 | 工作 |
|---|---|
| 开工 | 把 Issue 标签自己改成 `状态:实施中`（不用申请）；建 `feature/<模块>-<简述>` 分支 |
| 开发 | 按契约开发；`npm run build` 必须过（TypeScript 编译零报错） |
| 提 PR | 转 `Ready` 时把标签改成 `状态:待验收`；正文按附录 B.1 写，附构建输出 |
| 收到复审 | 按 `BLOCK-n` 编号逐条整改；**不要自行合并** |

#### 职责权重

- **前端实现（65%）**：4 个页面、身份态、路由守卫、金额换算唯一入口
- **联调（20%）**：与后端接口对齐、错误码处理、边界状态渲染
- **容器化（15%）**：Dockerfile 与 nginx 配置

#### 不负责

- 不写 `backend/` 下任何文件
- **不碰 `docker-compose.yml`**（陈展鸿独占，避免互相覆盖）
- 不引入第二套样式层（MUI / Element Plus / Ant Design 一律不用）
- 不在前端拼接或传递任何身份参数（`?userId=` 这类写法禁止）
- 不自行合并 PR、不自行关闭 Issue

## 四、协作规范

### 4.1 Kickoff 清单（新成员加入时执行，约 20 分钟）

| # | 内容 | 时长 |
|---|---|---|
| 1 | 项目定位：一条可验证的账目链路；V1 三项范围与阶段计划（README） | 4 min |
| 2 | 环境：`cp .env.example .env && docker compose up -d`，确认能起 | 4 min |
| 3 | Git 流程：分支命名 / commit 格式 / PR 写法；**必须 `git clone`，不要 `git init`** | 4 min |
| 4 | 文档地图：PRD / architecture / decisions / handbook / 分工书 各管什么、谁维护 | 4 min |
| 5 | 状态机与开工门禁（§4.6）+ 沟通渠道（§4.8） | 4 min |
| 6 | 认领第一个 Issue，完整走一遍 分支 → 提交 → PR → 复审 | — |

### 4.2 文件边界（防互相覆盖）

| 文件 / 目录 | 归属 |
|---|---|
| `docker-compose.yml` | **陈展鸿独占** |
| `frontend/Dockerfile`、`frontend/nginx.conf` | 包伟榕 |
| `docs/architecture.md` §5 接口契约 | **冻结**；改动须经 Owner 裁定 |
| `docs/PRD.md` | 由 Owner 派发变更，任何人不自行扩大范围 |

### 4.3 Git 分支策略

```
main          ← 可运行、可演示（只接受 PR 合并；不直接 push）
  ├─ feature/backend-skeleton   （陈展鸿）
  ├─ feature/auth               （陈展鸿）
  ├─ feature/frontend-skeleton  （包伟榕）
  └─ feature/*、fix/*、docs/*   （其余任务）
```

- 分支命名：`feature/<模块>-<简述>`、`fix/<模块>-<简述>`、`docs/<简述>`；**禁止** `test`、`temp`、`w1` 这类命名
- Commit 格式：`模块: 做了什么`（如 `auth: 新增 JWT 签发与身份依赖`）
- 不设 `dev` 分支：阶段收口标志即集成门槛

### 4.4 PR 规范

- 仓库**不设自动 PR 模板**，正文自行撰写（体现思考），结构见 `handbook` 附录 B.1
- 流程不熟时先发 **Draft PR**，由复审人指出缺什么再转 Ready
- 关联 Issue 用 `Refs #n`，**不用 `Closes #n`**（`Closes` 会在合并时自动关 Issue，绕过验收）
- 合并方式：**merge commit**（保留 PR 上下文）；合并权在 Owner

### 4.5 复审分工

| 谁提的 PR | 谁复审 |
|---|---|
| 后端（陈展鸿） | 包伟榕 |
| 前端（包伟榕） | 陈展鸿 |
| Owner 直接提交的 | 陈展鸿或包伟榕（另一方） |
| 涉及 `architecture.md` §5 契约的改动 | **Owner 必须参与** |

- 原则：**谁没写谁审** —— 同一个人不得复审自己写的 PR
- 复审由 PR 提出后**自动触发**，不需要等 Owner 指派
- 复审人按附录 B.2 格式产出（`BLOCK-n` / `SUG-n`），**只报不改**；整改由作者完成
- **复审通过 ≠ 可以合并**：合并权在 Owner

### 4.6 状态机与开工门禁

> 权威定义在 `docs/development-handbook.md` **附录 B.5**，本节只给要用的部分。

| 状态标签 | 由谁置 | 什么时候 |
|---|---|---|
| `状态:待批准` | Owner | 建 Issue 时默认 |
| `状态:已批准` | **仅 Owner** | 放行，可开工 |
| `状态:实施中` | **开发者本人** | 开工时自己置，**不用问 Owner** |
| `状态:待验收` | **开发者本人** | PR 转 `Ready` / 整改完成之后 |
| `状态:待整改` | **复审人** | 提出 `BLOCK-n` 之后 |
| `状态:已完成` | **仅 Owner** | 验收通过并关闭 Issue 之后 |

规则：

1. **无 `状态:已批准` 不得开工**；例外：复审提出的整改、修阻塞（CI / 环境 / 语法）、提问与讨论
2. 同一时刻**只保留一个**状态标签，置新的先摘旧的
3. **Issue 仅 Owner 可创建 / 派发**；需要新任务时在 Issue / PR 评论提出需求与理由
4. **不得自行关闭 Issue / 合并 PR** —— 由 Owner 统一关闭与合并
5. **同一 PR 不得夹带未讨论的新功能** —— 新功能先开 Issue

### 4.7 评审与处置分级

| 档 | 含义 | 判据 |
|---|---|---|
| **A** | Owner 直接出手 | 不改变队友产出的语义（文档、规范、纯措辞） |
| **B** | 打回返工 | 只有作者能改（断言无效 / 逻辑错误 / DoD 缺失）—— 对应 **阻塞项** |
| **C** | 仅提示，不返工 | 提出来供下次注意，本次放行 —— 对应 **建议项** |

约定：

- 复审结论写在 **PR 评论**（不写私聊）；格式见 `handbook` 附录 B.2
- 结论必须附证据：写「命令 → 结果」，不写"应该没问题"
- **CI 绿 ≠ 验收通过**：CI 只证明测试通过，不证明测试有效
- B 档整改可与作者的下一批提交合并进行，不必为一个小组件单独开一轮

### 4.8 沟通渠道

| 渠道 | 用途 | 原则 |
|---|---|---|
| **GitHub Issue / PR** | 任务派发、复审、决策、交付回报 | **正式记录与唯一真相源**：一切要求与结论落在这里 |
| **群聊** | 日常同步、催办、紧急提问 | 只做提醒；说过的要求须落到 Issue / PR，避免"群里说了但仓库查不到" |
| **Owner 私聊** | 卡壳求助、流程疑问 | 卡住 15 分钟没头绪就问，附报错原文 + 做了什么 / 期望什么 / 实际什么 |

## 五、阶段计划与验收标准

> 完整阶段表见 `README.md`「阶段计划」。**同一时间只开当前阶段的 Issue**。

## 六、Review 节奏

### 6.1 常规

| 触发 | 动作 |
|---|---|
| 作者提出 PR | 交叉复审人**自动接管**，按附录 B.2 出意见（阻塞 / 建议分列） |
| 作者整改完成 | 复审人复检；通过后移交 Owner 终审 |
| Owner 终审通过 | 合并 `main`；Issue 标 `状态:已完成` 并统一关闭 |
| 阶段收口 | 独立验收方复跑 A / B / C 编号，产出验收报告 |

### 6.2 阶段验收会（约 30 分钟）

1. 逐条过收口标准，**每条都要有命令与真实输出**（不接受口头描述）
2. 未达标的记为遗留项，写明卡点与负责人
3. 达成后由 Owner 打开下一阶段 Issue 并放行

## 七、硬约束（V1 全程有效）

1. **身份只来自服务端 Token 解析** —— 任何接口不接受 `userId` / `role` 等身份入参。路径中的 `member_id` / `post_id` 是资源标识，不属于身份入参。
2. **金额全程整数分** —— 不得出现 float 参与金额运算。换算只允许发生在前端输入框那一次。
3. **零硬编码凭据** —— `.env` 必须被忽略；仓库只允许 `.env.example` 且只有占位符；JWT 密钥缺失即启动失败，不提供默认值。
4. **CORS 永不使用 `"*"`** —— 白名单走环境变量。
5. **验证结论一律写「命令 → 结果」** —— 不写"应该没问题"。
6. **交付状态严格分级** —— 「已跑通 / 已实现未验证 / 未做」三档必须如实标注，不得把"未验证"写成"通过"。
7. **范围冻结** —— V1 三项定完即冻结，加功能走新 Issue。
8. **不做科研化功能** —— 需要准确率 / 召回率 / 训练 / 数据集才能验收的功能一律不做（判定信号见 `docs/decisions.md`）。

## 八、回报格式

每人交付时按此结构回报，不带客套、不带修饰：

1. 文件清单（路径 + 一句话作用）
2. 执行过的命令 → 真实输出摘要
3. 验收对照表（逐条标三档状态 + 证据命令）
4. 契约疑问或偏离
5. 遗留问题

格式细则（PR 正文 / 复审意见 / 整改反馈）见 `docs/development-handbook.md` 附录 B。
