# SplitWay · 分途 — 开发流程与规范

> 版本：V4.0
> 日期：2026-10-12
> 变更：确立单人开发流程与自律规范 —— 四顶帽子（需求 / 实现 / 红队 / 验收）、状态机与开工门禁、评审分级、备份与安全底线
> 历史：V1.0（2026-09-28）首版

**核心理念**：SplitWay 不是"又一个记账 App"，而是一条**可被自动化验证的多人协作账目链路** —— 出行前把人凑齐（找搭子 → 建房间 → 审批），出行中把钱算清（记账 → 结算）；全程身份只信服务端、金额不碰浮点、每一步都有可执行的验收编号。

---

## 一、角色

| 角色 | 承担者 | 职责 |
|---|---|---|
| **Project Lead & Architect (Owner)** | 肖宇翔 | 范围冻结、架构与接口契约、Issue 派发与放行、PR 合并、验收签字 |

单人项目里，"分工"这件事的实质是**给同一个人戴上不同的帽子、并强制它们互相制约** —— 详见 §三。

---

## 二、开发流程

```
Issue（Owner 派发 + 打「状态:已批准」）
  → 设计进 docs（决策进 decisions.md，契约进 architecture.md）
  → 实现（feature/<模块>-<简述> 分支）
  → 提交 PR（正文按 handbook 附录 B.1，附「命令 → 结果」）
  → 复审（换戴红队帽，按 BLOCK-n / SUG-n 编号逐条过）
  → 整改（按同一编号回填）
  → 独立验收（复跑 A / B / C 编号）
  → Owner 合并 main、关闭 Issue
```

### Git 分支策略

```
main          ← 可运行、可演示（只接受 PR 合并；不直接 push）
  ├─ feature/<模块>-<简述>
  ├─ fix/<模块>-<简述>
  └─ docs/<简述>
```

- 分支命名**禁止** `test`、`temp`、`w1` 这类
- Commit 格式：`模块: 做了什么`（如 `auth: 新增 JWT 签发与身份依赖`）
- 合并方式：merge commit（保留上下文）

### 不设 `dev` 分支

本项目按阶段推进，**阶段收口标志本身就是集成门槛**，再加一层 `dev` 只会多一次合并。

## 三、四顶帽子：单人项目怎么自我制约

一个人做项目，最大的风险不是写不完，是**没人反对你**。所以给同一个人规定四顶帽子，并且**不许同时戴**：

| 帽子 | 做什么 | 硬规矩 |
|---|---|---|
| **需求帽** | 定范围、派 Issue、放行 | 范围一旦冻结，加功能必须新开 Issue |
| **实现帽** | 写代码 | 只按已冻结的契约写；有异议在 Issue 提，**不许边写边改契约** |
| **红队帽** | 挑错：越权、逻辑矛盾、declare-了但没做到 | **只报不改** |
| **验收帽** | 复跑 A / B / C，只认命令输出 | **不看意图、只看结果** |

**两条不可妥协**：

1. **红队与实现必须分开做** —— 写完不当场顺手续审，等于自己给自己批卷子。
2. **实现帽与验收帽必须分开做** —— 验收结论以「命令 → 结果」为准，不以"我觉得没问题"为准。

## 四、状态机与开工门禁

> 权威定义在 `development-handbook.md` **附录 B.5**，本节只给要用的部分。

| 状态标签 | 何时置 |
|---|---|
| `状态:待批准` | 建 Issue 时默认 |
| `状态:已批准` | 放行，可开工 |
| `状态:实施中` | 开工时自己置（**不用申请**） |
| `状态:待验收` | PR 转 `Ready` / 整改完成之后 |
| `状态:待整改` | 复审提出 `BLOCK-n` 之后 |
| `状态:已完成` | 验收通过并关闭 Issue 之后 |

规则：

1. **无 `状态:已批准` 不得开工**；例外：复审提出的整改、修阻塞（CI / 环境 / 语法）、提问与讨论
2. 同一时刻**只保留一个**状态标签，置新的先摘旧的
3. **同一 PR 不得夹带未讨论的新功能** —— 新功能先开 Issue
4. **不得自行合并 PR / 关闭 Issue** —— 由 Owner 统一处理
5. PR 用 `Refs #n`，**不用 `Closes #n`**（`Closes` 会在合并时自动关 Issue，绕过验收）

## 五、评审与处置分级

| 档 | 含义 | 判据 |
|---|---|---|
| **A** | 直接出手 | 不改变产出的语义（文档、规范、纯措辞） |
| **B** | 打回返工 | 断言无效 / 逻辑错误 / DoD 缺失 —— 对应 **阻塞项** |
| **C** | 仅提示，不返工 | 提出来供下次注意 —— 对应 **建议项** |

- 复审结论写在 **PR 评论**；格式见 `development-handbook.md` 附录 B.2
- 结论必须附证据：写「命令 → 结果」，不写"应该没问题"
- **CI 绿 ≠ 验收通过**：CI 只证明测试通过，不证明测试有效

## 六、硬约束（V1 全程有效）

1. **身份只来自服务端 Token 解析** —— 任何接口不接受 `userId` / `role` 等身份入参。路径中的 `member_id` / `post_id` 是资源标识，不属于身份入参。
2. **金额全程整数分** —— 不得出现 float 参与金额运算。换算只允许发生在前端输入框那一次。
3. **零硬编码凭据** —— `.env` 必须被忽略；仓库只允许 `.env.example` 且只有占位符；JWT 密钥缺失即启动失败，不提供默认值。
4. **CORS 永不使用 `"*"`** —— 白名单走环境变量。
5. **验证结论一律写「命令 → 结果」** —— 不写"应该没问题"。
6. **交付状态严格分级** —— 「已跑通 / 已实现未验证 / 未做」三档必须如实标注，不得把"未验证"写成"通过"。
7. **范围冻结** —— V1 三项定完即冻结，加功能走新 Issue。
8. **不做科研化功能** —— 需要准确率 / 召回率 / 训练 / 数据集才能验收的功能一律不做（判定信号见 `decisions.md`）。

## 七、备份与安全底线

单人项目没有第二个人帮你找回东西，所以这几条是硬性的：

| 规矩 | 说明 |
|---|---|
| **改文件前先备份** | 改动源码/文档前先留一份原样（`_backup_*/`，已在 `.gitignore` 里）；改动前先 `cmp` 校验备份一致 |
| **推 GitHub 前先核对「什么会被推上去」** | `git status` 逐个看，确认 `.env`、`node_modules`、`dist`、备份目录都被忽略；**只看字节数不够** |
| **凭据永不入仓** | `.env` 只在本地；`.env.example` 只放占位符；密钥泄露立即轮换 |
| **密钥是本机生成的随机值** | 对外暴露（分享链接 / 公网）前必须更换 |
| **代码写完 ≠ 代码能跑** | 必须真实执行一次（`docker compose up -d` + `pytest`），阅读替代不了执行 |

## 八、阶段计划与验收标准

> 完整阶段表见 `README.md`「阶段计划」。**同一时间只开当前阶段的 Issue**。

| 阶段 | 收口标准 |
|---|---|
| **阶段1 · 立柱** | `cp .env.example .env && docker compose up -d` 三服务可用；浏览器能注册并登录；`pytest` 认证用例全绿 |
| **阶段2 · 主链路** | 浏览器里**手工**走通全链（发帖 → 申请 → 审批 → 记账 → 结算）；前端全程可操作 |
| **阶段3 · 收口** | 把手工链路**固化为可重放脚本**，A / B / C 编号全部复跑通过 |

### 单项目的验收标准

| 项 | 验收（可执行、可观察） |
|---|---|
| **后端** | `docker compose run --rm backend pytest -q` 退出码 0；`scripts/test_idor.py` 全断言 403 且可重放；3 人均分 10000 分求和严格等于 10000 |
| **前端** | `npm run build` 通过（`vue-tsc --noEmit` 零报错）；`docker compose up -d` 后前端可打开；浏览器侧 `/api` 为同源请求 |
| **Owner** | 阶段收口标志达成判定；契约一致性终审；`main` 保持可运行 |

## 九、交付格式

每次交付按此结构记录，不带客套、不带修饰：

1. 文件清单（路径 + 一句话作用）
2. 执行过的命令 → 真实输出摘要
3. 验收对照表（逐条标三档状态 + 证据命令）
4. 契约疑问或偏离
5. 遗留问题

格式细则（PR 正文 / 复审意见 / 整改反馈）见 `development-handbook.md` 附录 B。
