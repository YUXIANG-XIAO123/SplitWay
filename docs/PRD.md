### 1.2 数据库选型（已冻结）

| 维度 | PostgreSQL 16（选定） | 与 V1 的关系 |
|---|---|---|
| 金额表示 | `BIGINT`（**整数分**） | D7：金额全程整数分，任何路径不得出现 float；B3 的断言依赖此口径 |
| 部分唯一索引 | 支持（`WHERE status IN ('pending','joined')`） | V1 需要"同一房间同一用户只能有一条有效成员记录"，由数据库约束兜底，不依赖应用层判断 |
| 行级锁 | `SELECT ... FOR UPDATE` 语义清晰 | 结算需防并发重复结算 |
| JSON 字段 | `JSONB` | V1 非必需，仅备忘 |

结论：**PostgreSQL 16 已冻结**（D4）。MySQL 因不支持部分唯一索引，V1 不采用。
金额表示以 D7 为准，**不使用 `NUMERIC` / `DECIMAL` 存放金额**。
依据：`docs/decisions.md` D4 / D7；契约见 `docs/architecture.md` §3。

## 2. 产品目标

一句话定位：SplitWay 是一个面向小群体出行的协作工具，围绕"找搭子 → 建房间 → 记账 → 结算"一条链路，把多人协作、成员状态流转、金额结算跑通。

本项目要证明的能力（三个正交目标）：

| # | 目标 | 判定方式 |
|---|---|---|
| G1 | 环境工程能力 | 干净机器上一条命令拉起后端 + 数据库 + 前端，配置全部外置，零硬编码凭据 |
| G2 | 端到端系统设计能力 | 多用户、有状态流转、有金额精度要求的完整业务闭环可自动化验证 |
| G3 | 安全意识与工程纪律 | 身份只信服务端，跨用户越权可被一条可重放脚本断言为 403 |

## 3. 用户故事

| 角色 | 用户故事 |
|---|---|
| 普通用户 | 作为普通用户，我想注册并登录账号，这样我才能以自己的身份发起或参与搭子与房间 |
| 普通用户 | 作为普通用户，我想浏览"找搭子"帖子并发帖（目的地 / 出发日期 / 人数需求 / 备注），这样我能找到同行的人 |
| 普通用户 | 作为普通用户，我想对感兴趣的搭子帖申请加入，这样我能表达参与意愿并等待房主处理 |
| 房间创建者 | 作为房间创建者，我想基于搭子帖创建房间并审批申请，这样我能控制房间成员的确定性 |
| 房间创建者 | 作为房间创建者，我想在房间内记账并触发结算，这样我能把共同花费算清并给出每人应付金额 |
| 房间成员 | 作为房间成员，我想在房间内查看成员状态与账单明细，这样我能知道谁在、花了多少、我该付多少 |
| 房间成员 | 作为房间成员，我想退出房间，这样我能在行程变动时退出并让账务状态明确 |

## 4. 需求池

优先级定义：P0 = V1 必须交付；P1 = V1 不做，仅留档；P2 = 锦上添花，V1 视余量。

### 4.1 P0 需求（V1 三项，不多不少）

#### P0-1 可复现环境

| 项 | 内容 |
|---|---|
| 需求 | 一条命令启动后端 + 数据库 + 前端；所有配置外置；零硬编码凭据 |
| 说明 | 使用 `docker compose` 编排三个服务（db / backend / frontend）；配置来自 `.env`，仓库只提交 `.env.example` |

验收标准（可执行、可观察）：

| # | 验收标准 | 执行方式 | 观察结果 |
|---|---|---|---|
| A1 | 干净环境一条命令可用 | 在干净机器或干净 checkout 上执行 `cp .env.example .env && docker compose up -d` | 三个容器均 `healthy`；浏览器打开前端地址可注册并登录成功 |
| A2 | 零硬编码凭据 | 对仓库执行凭据扫描脚本（如 `gitleaks detect` 或自写 `grep -rnE "(password|secret|token)\s*[:=]" --include=*.py --include=*.yml`） | 源码、`docker-compose.yml`、Dockerfile 中不含明文密码 / 密钥；`.env.example` 只有占位符 |
| A3 | 配置全部来自环境变量 | 执行 `docker compose config` | 展开结果中的数据库口令、JWT 密钥等均引用 `${VAR}`，无字面量 |
| A4 | 敏感文件被忽略 | 执行 `git check-ignore -v .env` 与 `git ls-files | grep -E "\.env$|/uploads/"` | `.env` 被忽略；仓库中不存在 `.env` 与上传文件 |
| A5 | 可干净停止与重建 | 执行 `docker compose down -v && docker compose up -d` | 数据卷可重建，A1 再次通过 |

#### P0-2 一条完整业务链路（找搭子 → 建房间 → 记账 → 结算）

| 子项 | 内容 | 覆盖能力 |
|---|---|---|
| 找搭子 | 用户可发布 / 浏览搭子帖（目的地、出发日期、需求人数、备注） | 基础 CRUD 与列表 |
| 建房间 | 房主基于帖子创建房间；用户可申请加入；房主审批；成员状态流转 | 多用户协作、成员状态机 |
| 记账 | 房间内 joined 成员可新增账单（金额、付款人、参与分摊的成员）；分摊在所选参与人范围内均分（D8） | 金额精度、参与人范围均分 |
| 结算 | 房间可触发结算，输出每个成员的应付 / 应收金额 | AA 结算、幂等 |

成员状态机（V1 固定为四态）：

| 状态 | 含义 | 允许的迁移 |
|---|---|---|
| pending | 已申请，待房主审批 | → joined（房主通过）/ → rejected（房主拒绝）/ → left（申请人撤回） |
| joined | 已加入成员 | → left（退出） |
| rejected | 已被拒绝 | 终态 |
| left | 已退出 | 终态 |

房主在创建房间时自动写入一条 `role=owner, status=joined` 记录，且**不占** `member_limit` 名额；房主不可退出（V1）。

验收标准（可执行、可观察）：

| # | 验收标准 | 执行方式 | 观察结果 |
|---|---|---|---|
| B1 | 自动化测试全绿 | 执行 `docker compose run --rm backend pytest -q` | 退出码 0，全部用例通过 |
| B2 | 两个不同账号可真实走完整链路 | 端到端脚本（Playwright 或 httpx 脚本）用账号 U1、U2 执行：注册→登录→发帖→申请→审批→记账→结算 | 全流程无手工干预完成；U1 与 U2 的 token 互相独立 |
| B3 | 金额精度（除不尽场景） | 测试用例：3 人房间，账单合计 `100.00` 元，按人头均分 | 三人应付金额之和 `== 100.00`（以分为整数运算，断言无浮点误差）；余数按最大余额法分配，即按 userId 升序前 r 名各多 1 分（D9），规则固定且被断言 |
| B4 | 成员状态流转受约束 | 测试用例：成员处于 `pending` 时调用记账接口 | 返回 **403**，账单未被创建 |
| B5 | 结算幂等 | 测试用例：对同一房间连续调用两次结算 | 第二次不产生新的结算结果（金额一致，或返回"已结算"）；无重复扣减 |
| B6 | 非房主不能审批 | 测试用例：U2（非房主）调用审批接口处理 U1 的申请 | 返回 403；成员状态不变 |

#### P0-3 安全基线

| 项 | 内容 |
|---|---|
| 需求 | 身份一律来自服务端会话 / Token 服务端解析；禁止任何接口从前端接收 userId / role 等身份参数 |
| 说明 | 用户身份从 `Authorization: Bearer <token>` 中由服务端解析；所有涉及"谁在操作"的接口不接受前端传入的身份标识 |

验收标准（可执行、可观察）：

| # | 验收标准 | 执行方式 | 观察结果 |
|---|---|---|---|
| C1 | 跨用户越权断言 403 | 可重放脚本 `scripts/test_idor.py`：U1 登录后访问 U2 的房间 / 账单 / 成员资源 | 全部返回 403；脚本可重复执行且结果稳定 |
| C2 | 接口不接受身份参数 | 遍历 OpenAPI schema（`/openapi.json`），检查所有请求体 / 查询参数 | 不存在 `userId` / `user_id` / `role` / `approverId` 等**操作者身份**入参。路径中的 `member_id` / `post_id` 是资源标识，不属于身份入参（口径见 `docs/architecture.md` §5.1） |
| C3 | JWT 密钥外置 | 检查源码与镜像 | 密钥仅从环境变量读取；不含硬编码默认密钥 |
| C4 | CORS 白名单 | 检查后端 CORS 配置 | 不使用 `allow_origins=["*"]`；只允许前端实际域名 / 端口 |
| C5 | 未认证访问被拒 | 无 token 直接调用需登录接口 | 返回 401，而非返回数据 |
| C6 | 上传目录不裸奔（若 V1 引入上传） | 检查静态资源路由与容器挂载 | **V1 不做上传（D15），本条标 N/A**；后续版本若引入上传，需满足 `/uploads/**` 不对外匿名可枚举、上传文件不进入 git |

## 5. 页面与交互说明（V1）

V1 需要 4 个页面，均围绕"找搭子→房间"链路。以下为文字线框，不作为视觉设计稿。

### 5.1 注册 / 登录页

- 顶部：产品名。
- 主体：切换"登录 / 注册"两个 Tab。
- 表单字段：用户名、密码（注册时二次确认）。
- 交互：登录成功后 token 存 `sessionStorage`（**不长期驻留 `localStorage`**），跳转"找搭子列表"；接口返回 401 时清空 token 并跳回本页。
- 说明：V1 采用用户名 + 密码（D12），不引入邮箱 / 短信验证。

### 5.2 找搭子列表页

- 顶部：当前登录用户 + 退出按钮；"发布搭子帖"按钮。
- 主体：帖子卡片 / 表格列表，每条展示目的地、出发日期、需求人数、发起人、状态。
- 交互：点击卡片进入帖子详情；可对自己的帖子执行删除。

### 5.3 帖子详情页

- 展示：帖子完整信息。
- 交互：
  - 非发起人可点"申请加入"，调用申请接口，状态变为"申请中"。
  - 发起人可点"创建房间"，跳转到房间页并成为房主。
  - 列表展示当前申请人及其状态（仅发起人可见审批按钮）。

### 5.4 房间页（核心页，含分区 / Tab）

| 分区 | 内容 | 交互 |
|---|---|---|
| 成员区 | 成员列表及状态（房主 / 已加入 / 申请中 / 已退出）；房间人数上限默认 20，配置可改（D11），房主不占名额 | 房主可对申请中成员执行"通过 / 拒绝"；**仅本人可退出，房主不可退出**（V1） |
| 记账区 | 账单列表（金额、付款人、参与分摊成员、时间）；新增账单表单 | **仅 `joined` 成员可新增账单**；`pending` / `left` 成员调用返回 **403**（B4）。金额输入限制两位小数，提交前转整数分。**账单删除仅房主可执行**（D21），非房主返回 403 |
| 结算区 | "结算"按钮与结算结果（每人应付 / 应收） | **仅房主可触发结算**；结算后结果只读：账单不可新增、不可删除，调用返回 **409**（D10）；重复点击幂等，返回既有结果不新建记录（B5） |

## 6. 同领域常见缺陷 → 本项目反向约束

本节把该领域广为人知的常见缺陷逐条转成 V1 的硬约束，纳入 P0 验收。

| 常见缺陷 | 风险 | 本项目约束 | 对应验收 |
|---|---|---|---|
| 身份靠前端传参（如 `?userId=`） | 越权（IDOR） | 身份只从服务端 Token 解析，接口不收身份入参 | C1、C2 |
| JWT 密钥硬编码 | 密钥泄露即可伪造身份 | 密钥仅来自环境变量 | C3、A2 |
| 数据库账号密码明文入库且未忽略配置 | 凭据泄露 | 提交 `.env.example`，忽略 `.env` | A2、A4 |
| CORS `allowedOrigins("*")` | 任意站点可携带凭据调用 | CORS 白名单 | C4 |
| `/uploads/**` 对外暴露、上传文件进 git | 文件枚举与泄露 | 上传目录不匿名可枚举；上传文件不入 git（V1 不做上传，C6 标 N/A） | C6 |
| 测试几乎为零，回归无保障 | 回归无保障 | 核心链路 + 越权均有自动化用例 | B1、B2、C1 |

| N4 | 旅伴智能匹配 / 推荐排序 | 需要排序指标或匹配准确率 | 落入 N1 |
| N5 | 数据统计 / 可视化大屏 | 需要业务指标定义 | V1 无数据量，产出无意义，占用工期 |
| N6 | 管理后台 | 出现独立于业务的后台权限体系 | 为后台单独设计权限体系会直接扩大 P0-3 的范围 |
| N7 | 不等额分摊（自定义每人份额） | 出现"按人设置不同金额"的录入 | 留 P1；V1 均分即可覆盖主链路 |

判定信号（总则）：**只要验收标准里出现准确率 / 召回率 / AUC / 训练 / 数据集 / 对照组，就是越界。**

补充约束（非功能，但同属硬边界）：

- 不复制任何第三方代码、配置或数据库结构；代码 100% 自研（clean-room）。
- 不引入"管理后台"（见 N6）。
- 不调用现成大模型 API 生成文案：属"跑通即算完成"的例外，不算科研化，但 V1 不放，避免引入外部依赖与密钥管理成本。
  （本条在 V1.0 曾编号为 N5；因 `docs/decisions.md` 第四节无对应编号，V1.1 起移入本节，不再占用 N 序列。）
