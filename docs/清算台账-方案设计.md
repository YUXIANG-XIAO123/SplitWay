## 0. 一句话

> **微信群收款解决「收钱」，没解决「算钱」。**
> 旅行中十几笔垫付互相交织，谁垫的、谁该摊多少、最后谁欠谁 —— 这一段是空的。
> 本方案把「算完之后怎么还」补成一条**有状态、有留痕、删不掉的清算台账**。

## 1. 边界（先划死）

### 1.1 永远不做

| 项 | 原因 |
|---|---|
| **接支付通道** | 一旦碰钱就要牌照、风控、对账、退款通道 —— 直接超出个人项目范围。**SplitWay 永远不碰钱**，还钱发生在微信 / 支付宝。 |

### 1.2 本方案不做

| 项 | 原因 |
|---|---|
| 真推送（微信 / 短信通知） | 要接外部服务、模板审核、用户授权；且**不改变内核**。用户要的不是"帮我催"，是"催过这件事有据可查"。 |
| 站内聊天 / 私信 | 引入消息系统，复杂度爆炸，且与"可信账本"无关。 |
| 争议仲裁（房主裁决谁对） | 有事件留痕就够。加仲裁就把项目变成"纠纷处理系统"。 |
| 精确最少转账笔数（NP-hard 最优） | 用**贪心上界**替代（见 §5），精确最优留 P2。 |
| 房间归档 / 数据保留策略 | 是另一个话题，可与"归档"合并到后续版本评估。 |
| 多币种 | 引入汇率来源问题（从哪取 / 缓存 / 离线），复杂度陡增。 |

### 1.3 一句话判定

> **只要一个功能要在系统外触达真实的人（推送 / 支付），或者要在系统内裁决人的对错（仲裁），就是越界。**

## 2. 与微信群收款的差异

> 事实依据：微信支付官方文档 `pay.weixin.qq.com/doc/user/4021838219`。
> 微信群收款本身做得不差 —— 差异不在"好不好用"，在**它覆盖的是哪一段**。

| 维度 | 微信群收款 | SplitWay 清算台账 |
|---|---|---|
| **核心定位** | 一次性**收款单** | 房间级**账本 + 清算台账** |
| 分摊计算 | ❌ **不做** —— 全靠人脑算好再发起 | ✅ 从账单自动算净额 |
| 记录垫付 | ❌ 不记 | ✅ 每笔账单记付款人 + 分摊人 |
| 多笔交织 | ❌ 十几笔要发十几张收款单 | ✅ 一次性汇总成净额 |
| 到账方式 | **自己经手钱**，实时进零钱 | **不碰钱**，还钱在系统外 |
| 「待确认」状态 | 不需要（到账即事实） | **必需**（钱在系统外流动） |
| 有效期 | 30 天 | 台账长期存在 |
| 修改 | 有人付款后不可改、不可撤 | 结算前可自由增删账单 |
| 审计留痕 | 收款记录在发起人手机里 | **双方共同可见、删不掉** |
| 定位 | 收钱 | **算钱 + 记清谁还欠谁** |

**结论**：两者不是竞品，是**上下游**。人算完账 → 在微信收钱 → SplitWay 负责"算账 + 还钱过程中的状态"。

## 3. 核心概念

```
账单（bills）──┐
               ├─→ 结算（settlement）─→ ① 每人净额（已有，settlement_items）
房间成员       ┘                     └─→ ② 待还项（新增，debts）★
```

- **① 净额**：回答"谁应收、谁应付多少" —— 已有实现
- **② 待还项**：把净额拆成"**谁给谁多少**"的具体条目，每条带独立状态 —— 本方案新增

一条债务 = 一笔具体的"张三 → 李四 ¥120.00"，可以单独标记、确认、争议、催办。

## 4. 状态机

```
        ┌──────────────────────────────────────────────┐
        │                                              │
        ▼                                              │
   ┌─────────┐  应付方标记   ┌──────────────┐  应收方确认  ┌──────────┐
   │  待还    │ ───────────→ │ 已转账·待确认 │ ─────────→ │ 已结清    │
   │ pending │              │ transferred  │            │ settled  │
   └─────────┘              └──────────────┘            └──────────┘
        ▲                          │
        │                    应收方否认「没收到」
        └──────────────────────────┘
```

| 状态 | 含义 | 谁能触发下一步 |
|---|---|---|
| `pending` 待还 | 结算后自动生成 | 应付方标记转账 |
| `transferred` 已转账·待确认 | 应付方声明"我转了" | 应收方确认 / 否认 |
| `settled` 已结清 | 应收方确认收到 | —— 终态 |
| `disputed`（回到 pending） | 应收方否认 | 应付方重新标记 |

**关键取舍：只有两个终态之外的状态转换，每一步都写事件流水。**

- 「否认」**不引入新的持久状态**，而是打回 `pending` + 记一条 `dispute` 事件 —— 避免状态机膨胀
- 已结清的条目**不可再改**（同账单结算后只读的口径）

## 5. 转账方案算法（一个技术决策）

**问题**：净额只说明"每人该收/该付多少"，但没说"谁转给谁"。直接配对的笔数可能很多。

### 决策：贪心配对 + 可证明上界，不做 NP-hard 精确最优

| | 做法 | 笔数 | 复杂度 |
|---|---|---|---|
| **采用** | 排序 + 双指针贪心：应付方按金额从大到小，依次配给应收方 | **≤ 非零净额人数 − 1** | O(n log n) |
| 不用 | 搜索 / DP 求精确最少笔数 | 可能再少 1 笔 | NP-hard，20 人需剪枝 |

**理由**：
1. 贪心每次配对**至少清掉一个人**，所以笔数上界是 `非零净额人数 − 1` —— **这是一个可以写死断言的确定值**
2. 精确最优只在极少数构造下比贪心少 1 笔，收益极小、复杂度却陡增
3. 房间上限 20 人，贪心结果已经足够好

**验收**：`转账笔数 ≤ 非零净额人数 − 1`（D6）。精确最优留 P2。

## 6. 数据模型

### 6.1 `debts`（待还项）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | PK | |
| `settlement_id` → `settlements` | FK | 由哪次结算产生 |
| `room_id` → `rooms` | FK | 冗余，便于按房间查询 |
| `from_user_id` → `users` | FK | **应付方** |
| `to_user_id` → `users` | FK | **应收方** |
| `amount_cents` | BIGINT | 整数分，`> 0` |
| `status` | VARCHAR(16) | `pending` / `transferred` / `settled` |
| `created_at` / `updated_at` | TIMESTAMPTZ | |

约束：`amount_cents > 0`；`from_user_id != to_user_id`。

### 6.2 `debt_events`（事件流水，A3 审计的落点）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | PK | |
| `debt_id` → `debts` | FK | |
| `actor_user_id` → `users` | FK | **谁做的** |
| `action` | VARCHAR(24) | `create` / `mark_transferred` / `confirm` / `dispute` / `remind` |
| `note` | TEXT NULL | 可选备注（如"用支付宝转的"） |
| `created_at` | TIMESTAMPTZ | **什么时候** |

**只增不改不删** —— 这是"不可抵赖"的物理保证。

### 6.3 不变式

```
Σ(debts.amount_cents where to_user = X) − Σ(from_user = X) == X 的净额
```

即：待还项完全解释净额，不多不少。**可作为断言。**

## 7. 接口草案

沿用现有嵌套风格（对照 `/api/rooms/{room_id}/bills/{bill_id}`）：

| 方法 | 路径 | 入参 | 出参 | 权限 |
|---|---|---|---|---|
| GET | `/api/rooms/{room_id}/debts` | `?status=` | 200 待还项列表（含每条的提醒次数） | 房间 joined/owner |
| GET | `/api/rooms/{room_id}/debts/{debt_id}/events` | — | 200 事件流水 | 房间 joined/owner |
| POST | `/api/rooms/{room_id}/debts/{debt_id}/transfer` | `{note?}` | 200 | **仅应付方** |
| POST | `/api/rooms/{room_id}/debts/{debt_id}/confirm` | — | 200 | **仅应收方** |
| POST | `/api/rooms/{room_id}/debts/{debt_id}/dispute` | `{note?}` | 200 | **仅应收方** |
| POST | `/api/rooms/{room_id}/debts/{debt_id}/remind` | — | 200 | **应收方 或 房主** |

**错误码**：
- 非相关方操作 → `403`
- 状态不允许该操作（如对 `settled` 再点 transfer）→ `409`
- 同一状态重复标记（幂等）→ `200` 且不重复记事件

| 动作 | 应付方 | 应收方 | 房主 | 其他 joined 成员 |

| 看待还项 | ✅ | ✅ | ✅ | ✅ |
| 看事件流水 | ✅ | ✅ | ✅ | ✅ |

| 确认收到 | ❌ 403 | ✅ | ❌ 403 | ❌ 403 |
| 否认「没收到」 | ❌ 403 | ✅ | ❌ 403 | ❌ 403 |
| 提醒 | ❌ 403 | ✅ | ✅ | ❌ 403 |

## 9. 验收编号（新增 L 组）

| # | 验收内容 | 判定（命令 → 结果） |
|---|---|---|
| **L1** | 结算后自动生成待还项，且总量解释净额 | `Σ待还项 == Σ正净额（应收方）` |
| **L2** | 非应付方不能标记转账 | 越权调用 → **403** |
| **L3** | 非应收方不能确认 / 否认 | 越权调用 → **403**，房主亦然 |
| **L4** | 确认后状态为 `settled`，事件 +1 | 状态与流水双断言 |
| **L5** | 否认后回到 `pending`，流水记 `dispute` | 状态与流水双断言 |
| **L6** | **转账笔数 ≤ 非零净额人数 − 1** | 3 人房间固定账单 → 笔数 ≤ 2 |
| **L7** | 每次状态变更都有事件（谁 / 何时 / 什么动作） | 逐条核对时间戳与 actor |
| **L8** | 提醒可被记录，且只有应收方 / 房主可发起 | 次数断言 + 权限 403 |
| **L9** | 已结清的条目不可再改 | 再调用 → **409** |

> L 组与现有 A / B / C 三组并列，同样要求**可重放脚本**（进 `scripts/`）。
>
> **为什么不用 D 组**：`decisions.md` 已把 `D1–D21` 用作**决策**编号，再用 D 做验收会撞车。
> 改用 **L（Ledger）**：语义清晰，且不与任何既有编号体系冲突。
