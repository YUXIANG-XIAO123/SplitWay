> 版本：v1.0 — 2026-09-28
> 读者：本项目的全部协作角色（含 AI 角色）与未来的自己
> 目标：让任何一个新加入的角色，在读完这一篇之后能独立开工

## 1. 这个项目是做什么的？

SplitWay · 分途是一条链：**找搭子 → 建房间 → 记账 → 结算**。

V1 只有三件事：

| # | 交付项 | 一句话 |
|---|---|---|
| 1 | 可复现环境 | 一条命令起全栈，配置全外置，零硬编码凭据 |
| 2 | 一条完整业务链路 | 多用户、有状态流转、有金额精度的完整闭环 |
| 3 | 安全基线 | 身份只信服务端；越权可被一条脚本断言 403 |

**V1 不做什么**，见 `docs/decisions.md` 第四节与 `docs/PRD.md` §7。

先读什么、按什么顺序读：

```
README.md  →  PRD.md  →  architecture.md  →  本手册  →  开工
  定位          范围        契约与任务表        流程
```

## 2. 第一步：装好本地环境

需要的东西：**Docker Desktop**（含 Compose）、Git、Node 22+（做前端时）、Python 3.13（做后端时）。

```
# 1) 拉代码
git clone <repo-url>
cd SplitWay

# 2) 配置
cp .env.example .env
# 打开 .env，把占位符换成真实值（JWT_SECRET 至少要 32 字符）

# 3) 起服务
docker compose up -d

# 4) 验证
docker compose ps          # 三个服务都应是 healthy
```

后端 `http://localhost:8000`，OpenAPI 文档 `http://localhost:8000/docs`，前端 `http://localhost:8080`。

**注意**：`.env` 永远不会被提交。如果你不小心提交了它，立刻做两件事：从 git 移除、**把里面泄露的所有密钥全部轮换**。

## 3. 仓库与分支

### 分支命名（统一）

| 类型 | 格式 | 例 |
|---|---|---|
| 功能 | `feature/<模块>-<简述>` | `feature/room-settlement` |
| 修复 | `fix/<模块>-<简述>` | `fix/idor-room-detail` |
| 文档 | `docs/<简述>` | `docs/v1-architecture` |

**禁止** `test`、`temp`、`w1`、`new`、`aaa` 这类随意命名。分支名是给人看的，也是给未来的自己看的。

### 提交流程

```
git checkout -b feature/room-settlement
# ...写代码...
git add -A
git commit -m "feat(room): 成员审批与四态流转"
git push -u origin feature/room-settlement
# 然后在 GitHub 发起 PR
```

### 开工门禁（重要）

| 规则 | 说明 |
|---|---|
| Issue 带 `状态:已批准` 才可开工 | `状态:待批准` 的不得开工 |
| `状态:待整改` 可直接改 | 无需重新申请 |
| 同一 PR 不得追加未讨论的新功能 | 新功能先开 Issue |
| **不得自行合并 PR** | 合并权在 Owner |
| **不得自行关闭 Issue** | 关闭权在 Owner，且统一关闭，不逐个关 |
| PR 用 `Refs #n`，**不要用 `Closes #n`** | `Closes` 会在合并时自动关 Issue，绕过验收环节 |

## 5. 代码规范

### 通用

1. **身份只来自服务端**。写任何接口前先问：这个接口有没有接收身份参数？有就是错的。
2. **金额只用整数分**。`amount_cents: int`。代码里出现 float 参与金额运算即返工。
3. **配置只从环境变量读**。源码里不出现任何口令、密钥的字面量。
4. **错误要显式**。401 / 403 / 404 / 409 / 422 语义见 `architecture.md` §5.7，不要全都返回 200 再包一个 code 字段。
5. **不做过度包装**。不自定义统一 Result 包装层 —— 统一包一层 `{code,message,data}` 会让 HTTP 状态码语义变模糊。

### 后端（Python）

- 类型注解写全；`Mapped[]` 声明式模型
- 事务边界写在 service 层，路由层不直接操作 Session
- 每个对外接口在 `tests/` 里有对应用例

### 前端（Vue 3 + TS）

- 只用 Tailwind，不引入第二套组件库
- 金额换算只允许出现在输入框那一处：`Math.round(yuan * 100)`
- token 优先放 `sessionStorage`，不长期驻留 `localStorage`

### 注释与文档

- 中文；解释"为什么这么做"，不复述代码
- 不用 emoji、颜文字
- 不写格言式、说教式措辞（例如"信任不是靠态度建立的"这类），平实陈述事实与后果

## 6. 你的第一个任务（Owner 派发后开始）

1. 读 `docs/PRD.md`，找到你负责的验收编号（A / B / C）
2. 读 `docs/architecture.md` §5 契约，确认你的实现范围
3. 在既有 Issue 下认领，或按 `状态:已批准` 的 Issue 开工
4. 实现完成 → 本地跑通 → 按附录 B.1 写 PR 正文 → 发起 PR
5. 等复审意见 → 按同一编号逐条整改 → 回填 → 等验收

## 7. 遇到问题怎么办（按顺序）

1. 先看 `docs/decisions.md` —— 这个问题大概率已经被决策过
2. 再看 `docs/architecture.md` §5 —— 契约层面是否已明确
3. 都不是，就在 Issue / PR 里提问，说明：你做了什么、期望什么、实际什么、报错原文
4. **不要自行改契约**。契约问题不要用代码绕过，列出来由架构层裁定

## 附录 A · 本地环境排错与 Token 指引

### A.1 常见问题

| 现象 | 处理 |
|---|---|
| `docker compose up` 后服务 unhealthy | `docker compose logs <服务名>` 看原始报错；多数是 `.env` 没配或端口占用 |
| 后端启动即退出 | 这是设计行为：关键环境变量缺失会直接失败。看日志里缺了哪个变量 |
| 前端 404 | 确认 `nginx.conf` 的 `/api` 反代目标与 compose 里的服务名一致 |
| 数据库连不上 | 确认 `db` 服务 healthy 后再起 backend；compose 已配 `depends_on` |

### A.2 Personal Access Token

Push 需要凭据时用 GitHub Personal Access Token（不要用账号密码）。

**用完立即作废**。token 一旦贴在任何聊天窗口、Issue、PR 里，就当它已经泄露 —— 去 GitHub Settings → Developer settings → Personal access tokens 撤销，然后重新签发。

## 附录 B · PR 与评论格式（参考手册，非自动模板）

> **Issue 创建权限**：**Issue 只能由 Owner 创建 / 派发**。其他角色如需新任务，在现有 Issue / PR 评论中提出（说明需求与理由），由 Owner 按模板建 Issue（目标 / 交付物 / DoD / 回报格式 / 边界）并打标签放行后，方可开工。
>
> **开工门禁**：Issue 必须带 `状态:已批准` 才能开工；`状态:待整改` 可直接改（无需重新申请）；**同一 PR 不得追加未讨论的新功能**（新功能先开 Issue）；PR 提出后等 Owner review 结论；交付后等验收，**不得自行关闭 Issue / 合并 PR**。例外：整改项、修阻塞（CI / 环境 / 语法）、提问与讨论。

> 仓库**不设自动填充的 PR 模板**：PR 正文请自行撰写（体现你的思考），以下格式供参考，按需取用。

### B.1 PR 正文建议结构

- 关联：`Refs #<编号>`（**不要用 `Closes`** —— PR 合并会自动关闭 Issue，绕过验收；Issue 由 Owner 统一关闭）
- 本版内容（`v_ — YYYY-MM-DD`）
- 本次修正（基于 `<reviewer>` 对 `<commit>` 的意见）—— 迭代 PR 必填；首次提交可写「首次提交」
- 变更清单（表格），状态分级严格：
  - ② 完成并自测（附验证命令与结果）
  - ① 已实现、待依赖（注明依赖 Issue / PR）
  - ③ 未开始（仅记录）
  - 真实缺口（双方均未提供）：单独列出
- 验证结果：完整命令 → 结果（例：`python -m pytest backend/tests -q` → `42 passed`）
- 状态：`Draft（不合并，待 review）` / `Ready for review`；未修改声明（冻结流程 / 契约 / 他人模块）
- 完成回报：分支名 + PR 链接 + HEAD + 测试结果 + CI 结果 + 文件 checksum
  - **checksum 口径**：用**仓库内字节**（LF 行尾）计算。Windows 工作区默认 CRLF，同一文件算出的值会不同；若用本地文件计算，请注明「Windows 工作区 CRLF 口径」，不要与仓库值混用

### B.2 复审意见格式（复审人发在 PR 评论）

```
# PR #<n> 复审意见 — <复审人>（<角色>）

> 审查对象：<分支 / commit / 主要文件>
> 审查结论：发现 N 项阻塞 + M 项建议，暂不合并
> 日期：YYYY-MM-DD

@<作者>
<总体判断：哪部分已通过；哪类问题必须处理；是否可合并>

## 阻塞项（N）
### BLOCK-01｜<一句话概括>
- 文件：
- 依据：<契约条款 / Issue 要求 / 行号>
- 问题：<具体，附证据>
- 要求：<怎么改 + 验收标准>
- 判定：阻塞合并

## 建议项（M，不阻塞）
### SUG-01｜<一句话概括>
- 文件：
- 问题：
- 要求：
- 判定：不阻塞
```

### B.3 整改反馈格式（作者发在 PR 评论）

```
@<复审人> 已按复审意见完成整改（N 阻塞 + M 建议），请复检。

## 整改明细
BLOCK-01｜<对应复审编号>
- 改动：<文件 + 具体改动>
- 验证：<命令 → 结果>

## 验证结果
<完整命令>
结果：<…>

## 当前状态
HEAD：<sha>　CI：<结论>　未修改：<声明>
```

### B.4 约定

- 编号一一对应：复审用 `BLOCK-n` / `SUG-n`，整改按同一编号逐条回填
- 结论先行；每条必须含「文件 / 问题 / 要求 / 是否阻塞」
- 验证结果一律写「命令 → 结果」，不写「应该没问题」
- 评审不代替整改：复审人只提要求与验收标准，修改由作者完成

## 附录 D · 验证方法

### D.1 为什么有这一条

"我改好了"和"改好了能被验证"是两件事。本项目的所有结论必须能被第三方复现。

### D.2 验证清单（必做）

| # | 步骤 |
|---|---|
| 1 | 在干净环境跑一遍（不是"在我机器上跑过"） |
| 2 | 记录完整命令与原始输出关键行 |
| 3 | 对错误路径也要验证（不只 happy path）：越权、非法状态、重复操作 |
| 4 | 边界值：金额 0 / 除不尽 / 单人分摊 / 满员 |
| 5 | 结论写"通过"必须附证据命令；写不出证据就写"未验证" |

### D.3 常见误区

| 误区 | 实际 |
|---|---|
| "测试全绿所以功能对" | 测试可能没覆盖你新加的分支 |
| "本地能跑所以环境没问题" | 本地有缓存和残留，干净环境才是验收环境 |
| "CI 绿了所以没问题" | CI 可能跳过了你那个模块（本项目 CI 有 `probe` 步骤，缺文件会 skip） |
| "接口返回 200 所以成功" | 越权场景返回 200 才是 Bug |

## 附录 E · AI 辅助开发

### E.0 为什么有这一条

本项目的执行层角色由 AI 承担。这不改变验收标准，但改变了几件事的做法 —— 这一节把它们写清楚，而不是让它们停留在默契里。

### E.1 提交前，人自己过一遍

AI 产出的代码**必须由 Owner 或对应角色的把关人过一遍**再合并。判断标准不是"读起来对不对"，而是：

- 这条实现对应哪个验收编号？
- 如果删掉这段代码，哪条验收会失败？
- 是否引入了我没要求的依赖或抽象？

### E.2 给 AI 的 prompt 要带边界

边界包括：**不许改什么**（冻结的契约、他人的模块）、**验收标准是什么**、**什么算完成**。

没有边界的 prompt 会拿到一个"看起来完整但悄悄扩大了范围"的结果。

### E.3 AI 顺手补出来的东西，单独提 Issue

AI 经常会顺带优化一些没被要求的地方。这些改动：**要么删掉，要么单独开 Issue**，不要混在本次 PR 里。混进来会让 review 无法判断"哪些是本次改动"。

### E.4 AI 的产出不改变验收标准

验收标准由 PRD 定义，不由实现定义。**不能因为"AI 实现起来麻烦"就下调验收标准**；也不能因为"AI 顺便实现了"就上调标准、扩大范围。

### E.5 交了不等于完了

AI 报告"完成"时，要按附录 D 独立复跑。AI 的自我报告**不是验收证据**，命令输出才是。

### E.6 红队与实现必须分离

审计角色与实现角色**必须是不同的人、不同的会话**。

同一个上下文里既写代码又验收，等于自己给自己批卷子 —— 这会系统性地漏掉自己的错误。这是本项目在协作机制上唯一不可妥协的一条。
